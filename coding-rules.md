# Правила написания кода — Devman

## Для чего этот файл

Этот файл — **чек-лист для ревью кода**. Предоставлен для того, чтобы AI-ассистент (opencode, Cursor, Claude и др.) **помогал находить ошибки и нарушения стандартов** в коде при ревью, отладке и рефакторинге.

**Как использовать:**
- При ревью кода — проверяй соответствие этим правилам
- При отладке — ищи проблему среди типичных ошибок
- При рефакторинге — следуй этим стандартам
- При возникновении сомнений — применяй правило из этого файла

**Формат правил:** `номер. Название — краткое онение`

## Топ-20 самых важных правил (быстрая шпаргалка)

| # | Правило | Почему |
|---|---------|--------|
| 1 | Называй понятно | Код читают люди, не машины |
| 2 | Избавляйся от мусора | Удаляй закомментированный код, print(), `.save()` |
| 3 | DRY (Don't Repeat Yourself) | Копипаста — источник багов |
| 4 | Функции делают одно дело | SRP — single responsibility |
| 5 | Избавляйся от магических чисел | Выноси в константы |
| 6 | Исключения — конкретные | `except ValueError`, не `except Exception` |
| 7 | Проверяй ввод | Не доверяй данным пользователя |
| 8 | Именуй в snake_case | Переменные, функции — snake_case |
| 9 | Правильный регистр | Константы — UPPER_CASE, классы — CamelCase |
| 10 | Используй f-strings | Современный формат, не `%s` |
| 11 | with open() | Файлы всегда закрываются |
| 12 | os.path.join() | Кроссплатформенные пути |
| 13 | .get() для словарей | KeyError — частая ошибка |
| 14 | enumerate() | Не `for i in range(len(x))` |
| 15 | comprehensions | `[x for x in items]` vs цикл |
| 16 | datetime — разделяй | date, time, datetime — разные типы |
| 17 | docstrings по PEP 257 | Документируй функции |
| 18 | Коммиты — атомарные | Один коммит = одна задача |
| 19 | .gitignore | Не коммить мусор |
| 20 | Тесты — сначала | TDD, минимум smoke-тесты |

## Названия и нейминг

1. **Подберите точные названия** — Названия должны быть понятны человеку. Компьютеру всё равно, a или `user_name`.
2. **Замените транслит на англоязычные названия** — Код читают как текст, транслит мешает пониманию.
3. **Избавьтесь от типов в названиях** — Не `list_of_users`, а `users`. Python — не типизированный язык.
4. **Начните название функции с глагола** — `get_user()`, `fetch_data()`, `calculate_total()` — действие в начале.
5. **Избегайте глаголов в названиях переменных** — Переменные содержат данные, а не действия.
6. **Используйте правильный регистр букв** — `snake_case` для переменных/функций, `UPPER_CASE` для констант, `CamelCase` для классов.
7. **Поправьте множественное число в названиях** — `apples` если список, `apple` если один элемент.
8. **Не путайте порядок слов в названиях** — `user_name` — сначала что, потом какое. `name_of_user` — сначала свойство.
9. **Уберите числа из названий** — `MAX_RETRIES_3` — если изменится количество, придётся переименовывать.
10. **Разрешите конфликт имен** — Не используйте `dict`, `list`, `range` как переменные — это встроенные имена.
11. **Уточните название переменной** — Хорошее название подсказывает, что внутри.
12. **Уточните название класса в HTML** — Классы связывают HTML и CSS.
13. **Уточните название файла** — Название должно отражать содержимое.
14. **Уточните название функции** — Название подсказывает, что делает функция и что она вернёт.
15. **Подберите говорящие названия для переменных** — Названия должны сообщать полезную информацию.
16. **Не путайте файл и путь к нему** — Путь — это в файловой системе, адрес — URL.
17. **Избавьтесь от my_...** — Префикс `my_` избыточен.
18. **Избавьтесь от data в названиях** — Данные хранятся почти в каждой переменной.
19. **Используйте UPPER_CASE для переменных окружения** — `DATABASE_URL`, `API_KEY`.
20. **Дайте токену специфичное название** — `HH_TOKEN` вместо `TOKEN`, если несколько API.
21. **Используйте общепринятые сокращения** — `i` для индекса, `db` для базы данных, не `indexator`.
22. **Покажите чем отличаются переменные** — `letter_begin`, `letter_middle`, `letter_end` — читающему понятно.
23. **Запретите полю повторяться** — Уникальные поля должны быть помечены как `unique=True`.
24. **Разрешите полю повторяться** — Уникальность не всегда нужна.

## Функции

39. **Сделайте функцию требовательной к качеству входных данных** — Часть аргументов обязательна, часть нет.
40. **Укажите default value для аргумента функции** — Опциональные аргументы через `=`.
41. **Избавьтесь от лишних функций** — Если не упрощает — уберите.
42. **Соберите код CLI в одном месте** — Функции нельзя переиспользовать, если внутри `print`/`input`/`argparse`.
43. **Сделайте функцию требовательной к входным данным** — Не обязаны работать с любым вводом.
44. **Откажитесь от модификации входных аргументов** — Python передаёт ссылку на объекты, мутация неявна.
45. **Разбейте функцию на части** — Блок кода > половины экрана — пора бить на функции.
46. **Вынесите копипасту в функцию** — Дублирование кода — копипаста.
47. **Вынесите общие функции в отдельный файл** — Общие утилиты — отдельно.
48. **Укажите все аргументы функции** — Функция не должна зависеть от глобального состояния.
49. **Отделите обработку данных от ввода-вывода** — Функция делает одно: либо скачивает, либо читает, либо считает.
50. **Сделайте функцию чистой** — Чистая функция не имеет побочных эффектов.
51. **Привяжите функцию к предметной области** — Абстрактная функция — непонятно зачем.
52. **Вынесите решение проблемы наружу функции** — Функция либо возвращает данные, либо бросает исключение.
53. **Распакуйте параметры функции** — Используйте `*args`, `**kwargs` для гибкости.
54. **Упростите функцию** — SRP: функция делает одно дело.
55. **Высушите функцию** — Не повторяйтесь внутри функций.
56. **Не используйте mutable types как аргумент по умолчанию** — `def foo(items=[])` — опасно!

## Условия и булева логика

57. **Сделайте except избирательным** — Указывайте конкретное исключение, не `except Exception`.
58. **Избавьтесь от сравнений с True/False** — `if value == True` → `if value`.
59. **Избавьтесь от сравнений с None** — `if x is None` → предпочитайте `if not x` где уместно.
60. **Избавьтесь от сравнений с нулём** — `== 0` → `not x` или `x == 0` осмысленно.
61. **Избавьтесь от сравнений с пустым списком/словарём** — `== []` → `not x`.
62. **Избавьтесь от сравнений с пустой строкой** — `== ''` → `not x`.
63. **Вычислите булево значение без if** — Результат сравнения — всегда `True`/`False`.
64. **Разверните if, сделайте код более плоским** — Вложенные `if`/`else` усложняют понимание.
65. **Проверьте работу условий if** — Условие может работать всегда или никогда.
66. **Сократите размер блоков try...except** — Только нужный код внутри `try`.

## Циклы

67. **Замените простые циклы на comprehensions** — List/dict comprehensions降低复杂度.
68. **Используйте enumerate для нумерации списков** — `for i, item in enumerate(items)`.
69. **Упростите цикл while** — `while condition` вместо `while True... break`.
70. **Избавьтесь от цикла while** — `for` безопаснее, не застрянет в бесконечном цикле.
71. **Настройте enumerate** — `enumerate(items, start=1)` — с единицы.
72. **Настройте range** — `range(1, n)` — с единицы.
73. **Воспользуйтесь циклами** — Делайте одно и то же для нескольких объектов через `for`.
74. **Итерируйтесь по списку/словарю напрямую** — Не `for i in range(len(x))`, а `for item in x`.
75. **Сократите уровень вложенности** — Глубокая вложенность — признак плохого дизайна.

## Строки

76. **Сделайте строку многострочной** — Символы `\n` в строке — используйте multiline string.
77. **Используйте шаблоны вместо сложения строк** — f-strings и `.format()` нагляднее.
78. **Используйте встроенные возможности format** — format() — швейцарский нож для строк.
79. **Разбейте длинные строки на части** — Горизонтальная прокрутка — признак длинной строки.
80. **Избавьтесь от устаревшего способа форматирования строк** — `%s` — старый синтаксис, используйте f-strings.
81. **Выберите основной вид кавычек** — Одинарные `'` или двойные `"` — выберите и придерживайтесь.
82. **Используйте textwrap.dedent** — multiline строки с отступами выравнивайте через `dedent`.
83. **Уберите лишние преобразования типов** — `str(len(items))` — `len(items)` уже int, f-string сам преобразует.
84. **Используйте возможности многострочной строки** — `\n` в строках — проблема.

## Структуры данных

85. **Упростите создание словаря** — `{k: v for k, v in items}` вместо пустого dict + цикл.
86. **Упростите создание списка** — `[x for x in items]` вместо пустого list + цикл.
87. **Спрессуйте изменения в словаре** — `d[k] = v` вместо промежуточных переменных.
88. **Используйте defaultdict** — Не нужно проверять `if k in d`.
89. **Используйте Counter** — Подсчёт повторов — стандартная задача.
90. **Очистите код от индексов** — `record[1][0]` — держите структуру в голове. Используйте имена.
91. **Спрячьте избыточные индексы** — `s[1:-1]` — используйте слайсы правильно.
92. **Упростите доступ к данным** — `data['key1']['key2']` — держите в голове. Используйте промежуточные переменные.
93. **Протестируйте программу на неполном словаре** — `.get(key)` vs `['key']` — разное поведение.

## Исключения

94. **Отложите перехват исключения** — "Бросай рано, обрабатывай поздно".
95. **Сделайте except избирательным** — Конкретный тип, не `except Exception`.
96. **Введите свой тип исключений** — `CustomError` вместо generic `Exception`.
97. **Не перехватывайте исключения просто так** — Перехват без действия — бессмыслен.
98. **Используйте contextlib.suppress** — `suppress(Exception)` вместо пустого except.
99. **Сократите размер блоков try...except** — Только нужный код, не вся функция.
100. **Не переизобретайте механизм исключений** — Исключения уже есть — используйте стандартные.
101. **Проверьте обработку исключений** — except-блок тоже может быть сломан.
102. **Обработайте DoesNotExist** — При `.get()` запись может не найтись.
103. **Обработайте MultipleObjectsReturned** — `.get()` вернёт ошибку, если записей больше одной.

## Django

150. **Добавьте файл с зависимостями** — `requirements.txt` с версиями.
151. **Зафиксируйте версии пакетов** — Новые версии могут сломать обратную совместимость.
152. **Уменьшите количество необходимых библиотек** — Меньше зависимостей — проще разобраться.
153. **Расскажите в README о переменных окружения** — Нестандартные переменные — документируйте.
154. **Сделайте поле обязательным** — Не все поля могут быть пустыми.
155. **Запретите отрицательные цены в БД** — Цена не может быть отрицательной.
156. **Запретите отрицательное/нулевое количество товаров** — `quantity > 0`.
157. **Разрешите полям оставаться пустыми** — `blank=True`, `null=True` где нужно.
158. **Запретите null в строковых полях** — `null=True` для CharField — головная боль.
159. **Запретите каскадное удаление** — `on_delete` — всегда.

## Инструменты проверки

Эти команды используй для автоматической проверки кода:

```bash
# Форматирование
black .
isort .

# Линтинг
flake8 .
pylint .

# Типизация
mypy .

# Тесты
pytest .

# Всё вместе (pre-commit)
pre-commit run --all-files
```

### Приоритет применения правил

1. **Безопасность** — секреты, SQL-инъекции, XSS
2. **Логика** — баги, которые сломают программу
3. **Читаемость** — нейминг, структура
4. **Стиль** — форматирование, порядок импортов

### Когда правило можно нарушить

- Есть веская причина, зафиксированная в комментарии
- Линтер явно требует обратного
- Рефакторинг в процессе (временно)
